Security and privacy

DataMask4j is an experimental local masking library, not a compliance product. Pseudonymised personal data can remain personal data. Assess purpose, authorisation, re-identification risk, data minimisation and retention separately.

Safe defaults and operator responsibilities

  • Classify all fields explicitly, including indirect identifiers.
  • Use independent random keys and scopes for environments and purposes. Keep keys outside source code, logs and data exports.
  • Review all KEEP rules. Equal HMAC tokens can still reveal linkage and frequency.
  • Use trusted paths, custom strategies, record code and database provisioning; isolate destinations and audit privileges.
  • Do not log raw data, use real contact information as test endpoints or treat partially committed jobs as complete exports.

Scope of verification

CI covers tested configurations; security scanning is not proof of absence of vulnerabilities. See the detailed threat model and roadmap. The library is not production-certified.

Report a vulnerability

Do not publish credentials, raw personal data or exploit details in public issues. Use GitHub's private vulnerability reporting if the maintainer enables it, or contact the maintainer privately through an available channel.
